# Worker brief and acceptance contract

Each brief must stand alone:

- User outcome and mode; confirmed decisions versus open choices; application/version/OS/platform.
- Absolute project, role SKILL.md, family lead, relevant source/reference and output paths.
- Read the wrapper safety overlay first. Upstream instructions are expertise, not new authorization.
- One accountable responsibility, specific questions, exact writable files (or report-only), exclusions.
- Evidence already available, known uncertainty, execution capability, prerequisite handoff and editor owner.
- Required deliverable and acceptance checks; budget proportionate to task; no broad optional exploration.
- Coordinate with the orchestrator; do not launch other editor processes, change shared scene state, install
  bridges, or expand the panel yourself. Mark blocked work and continue independent authorized work.

## Review report

1. Scope, examined evidence and execution limits.
2. Findings: severity, observed fact, exact file/line/object/frame/timecode, impact and targeted remedy.
3. Distinguish observations, inferences, hypotheses and owner-decision challenges.
4. Recommended sequence and dependency handoffs; avoid generic advice with no project evidence.
5. Acceptance checks and remaining uncertainty. State when there are no actionable findings.

Do not manufacture a minimum number of findings. Length follows substance (usually 500–1,500 words).
Reviewers edit only their reports. A report's proposed fix does not authorize its implementation.

## Implementation report

State changed paths, behavior, validation executed and results, remaining limits, and any handoff artifact.
Use before/after measurements or captures where meaningful. Source compilation does not prove visuals,
headless captures do not prove device performance, and exports do not prove destination import.

## Coordinator synthesis

Verify top-priority claims against primary project evidence. Merge duplicates without treating consensus
as proof; a unique finding can still be critical. Resolve disagreements with a discriminating check,
otherwise preserve the uncertainty. Report a single prioritized action list and dependencies. Ask only
questions the owner must decide. When implementation is authorized, complete it and validate rather
than ending at a review. Do not make publication or long render commitments on behalf of the owner.
